# Experts (Native Expert & Team Registry)

## Overview
Native Expert identities and Team orchestration live entirely inside Cognate shared state.
`service.ts` is the single capability mutation boundary: every command commits a typed,
version-checked `state.changed` snapshot through the Cognate runtime — there is no second
database and no event emitter. Canonical state (`schema: 1`) is the versioned thread
`experts:registry` (`EXPERTS_THREAD`); large sections are published as hash-addressed,
immutable partition threads behind a root manifest (`schema: 2`). The completion bridge
reconciles run outcomes into Assignments; admission derives concurrency keys from
authoritative state only; billing reserves model spend before dispatch. The authoritative
semantic anchors are the IDM in `.sea/interaction/interaction-model.sea`, loaded in place by
`domain/index.ts` (`EXPERT_CAPABILITY_ANCHORS`) — the model is not copied into code.

## Invariants
- Every command commits a typed, version-checked `state.changed` snapshot through Cognate; no second database (`src/experts/service.ts:ExpertsService.command` module header).
- Team identity invariant: a Team may have only one Orchestrator, an active Team requires exactly one, membership is duplicate-free, and all members are active Experts (`src/experts/state.ts:assertTeamInvariant`).
- Only the human operator may manage identities, configuration, reviews and settlement; run-context (expert) access is limited to the internal capability list and to tools present in `invoking.execution.tools` (`src/experts/service.ts:ExpertsService.command`).
- Delegation: only the authorized Team Orchestrator (depth 0, shared team scope, holding `team_delegate`) may delegate, and only to a Specialist — never a second Orchestrator (`src/experts/service.ts:ExpertsService.command` case `team.delegate`; `src/experts/service.ts:ExpertsService.makeAssignment`).
- Idempotency: a reused command id with a different fingerprint throws `Idempotency identity was reused for different work`; receipts store the command fingerprint and result (`src/experts/state.ts:mutateExperts`).
- Human settlement gates: `accept` review requires an independent Expert's observable checks (`read`/`bash`/`run_code` tool completions) from a descendant run, and `team.settle` acceptance requires a reviewed `accept` verdict, disposition `result`, and no unresolved descendant failures/uncertainties/effect states (`src/experts/service.ts:ExpertsService.command` cases `team.review`, `team.settle`).
- Handoff provenance: artifacts must belong to the run (`run.artifact` events) and evidence must cite observable events of the same run (`src/experts/service.ts:ExpertsService.command` case `team.handoff`).
- Memory provenance must cite existing Assignments, runs or messages; only a human may promote or replace `accepted` knowledge; scope elevation is denied (`src/experts/service.ts:ExpertsService.command` case `expert.memory.write`).
- Partition integrity: manifests are validated for section coverage and prefix-free (non-overlapping) trie paths; every touched partition is verified against its sha256 content address, identities against their partition path, and sections against manifest fingerprints; root manifests are refused above 900 KiB (`src/experts/persistence.ts:validateExpertManifestReferences`, `src/experts/persistence.ts:restoreExpertSectionEntries`, `src/experts/persistence.ts:readExpertRecords`, `src/experts/persistence.ts:prepareExpertManifestUpdate`).
- Sanitization: `publicItems` projections redact memory/receipts/audit entirely, drop private-team conversations and their messages/assignments, and strip `execution.context`; they are never used to restore authoritative state (`src/experts/persistence.ts:publicItemsFor`, `src/experts/persistence.ts:PartitionPayload`, `src/experts/state.ts:publicExperts`).
- Admission keys derive from authoritative state only (Experts registry, `workspaces` projection) — never run-supplied input; unknown/unclassifiable work fails closed to `WORKSPACE_EFFECTS_RESOURCE_KEY`; a forged or absent workspace id never mints a key (`src/experts/admission.ts:workspaceRecordFor`, `src/experts/admission.ts:workspaceEffectKeys`, `src/experts/admission.ts:createExpertAdmissionResourceKeys`).
- Team admission policy resolves only from authoritative Team metadata (`team.save`); client-supplied policy fields (`maxConcurrentRuns`, `admissionBatch`, `policy`, `limits`, `teamPolicy`) are refused at the capability layer (`src/experts/service.ts:ExpertsService.command` case `expert.converse`/`team.converse`; `src/experts/admission.ts:teamAdmissionKeys`).
- Billing: unknown prices are carried as null, never fabricated as zero; spending ceilings cannot be verified while unknown-price reservations exist; crash-interrupted reservations are booked conservatively (`reconciled-unknown`) and recovery re-dispatch proceeds under a new `:rN` generation — every attempt accounted exactly once (`src/experts/billing.ts:enforceCeilings`, `src/experts/billing.ts:reserveModelCall`).
- Retry safety: `team.retry` refuses blind replay when any descendant effect is `UNKNOWN_RECONCILIATION_REQUIRED` or `DISPATCHING`, refuses when an effect was confirmed `SUCCEEDED`, is root-only, and caps attempts at 3 (`src/experts/service.ts:ExpertsService.command` case `team.retry`).
- Context assembly marks retained memory as untrusted data and preserves unresolved commitments and pinned knowledge or fails the invocation (`src/experts/service.ts:ExpertsService.context`).
- Token estimates are estimates, never provider receipts: the accounting method is always labeled and hidden provider framing is covered only by the explicit `ENVELOPE_MARGIN_TOKENS` margin (`src/experts/economics.ts:estimateRequestTokens`, `src/experts/tokenizer.ts:tokenizerForRoute`).

## Side Effects
- All state writes go through `service.updateSharedState` on threads `experts:registry`, `experts:partition:v1:<section>:<path>:<hash>`, and `experts:billing:v1`, using `expectedVersion` CAS and `idempotencyKey` strings (`src/experts/state.ts:mutateExperts`, `src/experts/persistence.ts:writeImmutablePartition`, `src/experts/billing.ts:reserveModelCall`).
- Legacy `schema: 1` roots are migrated to manifest form with idempotency key `expert-state-migration:<version>:<fingerprint>` (up to 30 CAS retries) (`src/experts/state.ts:readExperts`, `src/experts/state.ts:mutateExperts`).
- Run lifecycle calls: `service.getRun`, `service.startRun`, `service.cancelRun` (idempotency `expert-cancel:<assignmentId>:<attempt>`), `service.resolveContinuation` (idempotency `expert-return:<id>:<attempt>`), `service.readProjection` (`model-config`, `workbench`, `workspaces`, `settings`, `experts`), `service.events` iteration (`src/experts/service.ts:ExpertsService.invocation`, `src/experts/bridge.ts:ExpertCompletionBridge.reconcile`, `src/experts/billing.ts:runInvocationInspector`).
- The bridge follows the live event stream (`follow: true`) and re-runs `reconcile` on `state.changed` for `EXPERTS_THREAD` plus `run.started|completed|failed|cancelled|waiting`; it logs failures to stderr and records `error` (`src/experts/bridge.ts:ExpertCompletionBridge.start`).
- `team.cancel` signals still-running descendant runs through `service.cancelRun` after the mutation commits (`src/experts/service.ts:ExpertsService.command` post-mutation block).
- The tokenizer lazily imports `gpt-tokenizer/encoding/<encoding>.js` and memoizes the module promise per encoding (`src/experts/tokenizer.ts:loadEncoding`).
- Admission is process-local by SDK contract — it is not distributed safety (`src/experts/admission.ts` module header).
