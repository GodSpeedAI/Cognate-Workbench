# Independent security review — T8 production identity, authorization and aggregate containment

- Reviewed: HEAD `e5154a488d20d4aa6d2cd4dc18f8cca2cdba5527` (branch `feature/expert-teams`) plus the uncommitted T8 change set (`git status --short`: 29 modified files, 8 untracked). Files examined line-by-line: `src/auth/identity.ts` (new), `src/capabilities/identityAdmin.ts` (new), `src/capabilities/aggregateContainment.ts` (new), `src/server.ts` (modified — policy, authenticator wiring, boot, hardening headers), `src/settings.ts`, `src/capabilities/settingsChange.ts`, `domain/index.ts`, `.sea/interaction/interaction-model.sea` (three new journey instances), `.generated/entry.tsx` (tracked, now token-bearing), `test/J-AUTH-SESSION.test.ts`, `test/J-AUTH-TENANT-ISOLATION.test.ts`, `test/aggregateContainment.test.ts`, `test/J-RW-AGGREGATE-CONTAINMENT.test.ts`, and the `devAuth: true` test-helper diffs. Framework surfaces the claims depend on were verified in `node_modules`: `cognate-runtime-bun/src/service.ts` (Connect RPC authorization for `readSharedState`/`updateSharedState`/`readProjection`/`invoke`), `cognate-runtime-bun/src/invoker.ts` (no result journaling on direct invoke), `cognate-kernel-cordis/src/kernel.ts` (KernelEvent is in-memory), `cognate-protocol-connect-bun/src/index.ts` (`devTokenAuthenticator` regex, `connectTransport` no-store), `cognate-execution/src/bubblewrap.ts` (timeout kill, `--die-with-parent`, argv construction), `cognate-execution/src/types.ts`/`capabilities.ts` (`timeoutMs` optional and passed through), `src/experts/governance.ts` (what `expertGovernedService` does and does not wrap), `src/agents/agentConfig.ts` and `src/projections/settings.ts` (settings.changed run path validation), `.gitignore` / `git ls-files .generated/` (tracked status). Date: 2026-10-17. No source, test, or configuration file was modified; this artifact is the only write.
- Method: full diff review (`git diff` + reading the new files at working-tree line numbers); adversarial derivation of concrete attack paths against each of the plan's three teeth (revocation replay, fail-closed aggregate quotas, tenant isolation); tracing every trust claim in the new code to the framework code that must uphold it (thread-state authorization, projection partitioning, result journaling, provider timeout enforcement); mapping the four new test files claim-by-claim to the teeth and enumerating what they do not prove. Static analysis only — no test suite run, no server started, no runtime behavior exercised; every runtime-dependent step in a finding is marked as such.

- Findings:

  1. **HIGH — The T8 system-owned ledgers are not covered by the ActionPolicy's `thread.state.update` guard: any authenticated session in tenant `local` can rewrite the identity ledger and forge the operator.** The runtime's remotely exposed `updateSharedState` RPC is gated only by the app's action policy (`node_modules/@godspeedai/cognate-runtime-bun/src/service.ts:316-317` → `authorize(caller, "thread.state.update", request.threadId)`), whose guard list at `src/server.ts:218` covers `EXPERTS_THREAD`, `experts:partition:*` and `SCHEDULES_THREAD` — T8 added `auth:identity:v1` (`src/auth/identity.ts:18`) and `containment:aggregate:v1` (`src/capabilities/aggregateContainment.ts:28`) to the same store but did not extend the guard, and `expertGovernedService` does not wrap shared-state RPCs (`src/experts/governance.ts:7-31`). Attack, concrete steps: (i) the operator uses `identity.session.issue` to provision a second identity in the operator's own tenant (`{tenant: "local", actorId: "bob"}` — accepted by design, `src/capabilities/identityAdmin.ts:44-56`), or an attacker steals that session token — exactly the theft threat revocation exists for; (ii) bob authenticates (caller `{tenant: "local", kind: "user"}` — derived server-side, so the tenant partition that protects other tenants does not help here, because bob *is* in tenant `local`); (iii) bob calls `readSharedState("auth:identity:v1")` — allowed, same tenant stream (`service.ts:310-313` keys the stream by `caller.tenant`); (iv) bob calls `updateSharedState` with `{snapshot: …}` appending a session record `{sid, identityId: "identity-<sha256("local\0operator").slice(0,16)>", tokenHash: sha256("wbs1.<bob's chosen 43-char body>"), status: "active", createdAt, expiresAt: <future>}` — the operator identity id is deterministic and offline-computable (`src/auth/identity.ts:126`), and the snapshot path is the same one `writeIdentityState` uses (`src/auth/identity.ts:101-110`); (v) bob presents `Bearer wbs1.<chosen>`: `authenticateSessionToken` (`src/auth/identity.ts:180-194`) finds the hash, sees `status: "active"`, unexpired, identity exists — and resolves bob's token to the full operator caller. Every `GRANTED_CAPABILITIES` grant at `src/server.ts:202-206` now applies. The same write access revives a revoked session (flip `status` back to `"active"`) and can release or fabricate `containment:aggregate:v1` slots. Remediation: add `IDENTITY_THREAD` and `CONTAINMENT_THREAD` to the `thread.state.update` system-only guard at `src/server.ts:218` (mirroring `EXPERTS_THREAD`), and consider guarding `thread.state.read` for the identity ledger too. This hole is untested: `test/J-AUTH-TENANT-ISOLATION.test.ts` proves isolation only for a *second* tenant (`acme`), which the per-tenant stream namespacing makes safe by construction; the dangerous case — a non-operator session *inside* tenant `local` — is never exercised.

  2. **MEDIUM — Any authenticated session can rewrite its tenant's settings via a direct `agent.config` run, bypassing every `settings.change*` validator — in tenant `local` that includes the aggregate containment quotas the T8 tooth depends on.** The validators (`isContainmentQuotas`, `isSpendingCeilings`, etc.) live only in the capability handlers (`src/capabilities/settingsChange.ts:78-94`); the durable write path is `startRun(agent.config, {kind: "settings.changed", …})`, whose run body emits the input verbatim (`src/agents/agentConfig.ts:44-46` — "the run body only emits") and whose projection fold merges whatever fields the event carries with no validation (`src/projections/settings.ts:11-38`). `startRun` is not restricted for `agent.config` by the action policy (`src/server.ts:217` guards only `EXPERT_AGENT`), and `test/J-AUTH-TENANT-ISOLATION.test.ts:83-96` proves a plain user session can drive this path end to end. Consequences for tenant `local` (again reachable by any provisioned local-tenant session per finding 1, and by the operator's own bug-runs): write `containment: {maxConcurrent: 256, cpuSecondsPerWindow: 864000, cpuSecondsPerExecution: 86400}` and the operator's configured ceiling is silently replaced (`readContainmentQuotas` enforces whatever is stored, `src/capabilities/aggregateContainment.ts:103-108`); write an *invalid* value and all contained work fails closed until repaired (a quota DoS). It also undercuts the `buildPolicy` comment that a non-operator session "holds no workbench capability authority" (`src/server.ts:195-198`) — it holds no *direct invocation* authority, but the run engine executes its acts with system-kind authority inside the tenant. Remediation: validate `settings.changed` inputs in the `agent.config` run (or fold-time) against the same validators, or restrict `run.start` for `agent.config` to system/operator callers. Test gap: no test attempts a quota-invalidating or quota-widening `settings.changed` run.

  3. **MEDIUM — The deployment-hardening headers are NOT on every response: successful Connect API responses bypass them, while the code comment claims otherwise and the test never checks that path.** `src/server.ts:641-645` states "every response carries the browser hardening headers", but the Connect handler branch returns the handler's response untouched: `return handler ? handler(request) : new Response("not found", { status: 404, headers: hardened() })` (`src/server.ts:664-667`) — only the 404 fallback, `/health`, and the static/UI paths get `hardened()` (`src/server.ts:661-675`). Every `200` from `/cognate.v1.RuntimeService/*` is emitted without `x-content-type-options`, `x-frame-options`, `referrer-policy`, COOP or CORP. Practical browser risk is modest (Connect replies are `application/json`, POST-only, same-origin, and the parenthetical CORS argument at `src/server.ts:642-644` is sound), but the stated invariant is false, and `test/J-AUTH-SESSION.test.ts:129-151` — named "headers are present on every response" — checks `/`, `/health` and a *404* API path only, never a successful API response, so it cannot catch the gap. There is also no `Content-Security-Policy` anywhere in `hardened()` (`src/server.ts:646-653`) even though `/app.js` embeds this boot's bearer token, making CSP the one header that would matter most against an XSS exfiltrating it. Remediation: wrap the handler response (clone + merge headers, or set them in a `Bun.serve` response transformer), add a CSP for the HTML entry, and extend the header test to a successful Connect call.

  4. **MEDIUM — This boot's cleartext session token is written into `.generated/entry.tsx`, a git-TRACKED file, so session material is sitting in the working tree and would enter git history on commit.** `src/server.ts:624-625` writes the token into the generated entry (`BROWSER_ENTRY_TEMPLATE(..., operatorSession.token)`), and `git ls-files .generated/` confirms the file is tracked and not ignored; the working-tree diff already contains a live-format token (`.generated/entry.tsx:13`, `const authToken = "wbs1.Mvbqfku…"`). This contradicts the design claim "The cleartext token exists in memory and the generated entry only" (`src/server.ts:443`) in that the generated entry is durable, version-controlled storage: a routine `git add` would commit a credential (revoked only at the *next* boot by `supersedeBootSessions`, `src/auth/identity.ts:241-250`, so valid for up to 24 h or until restart), and the file is world-readable under a default umask. Impact is bounded by the 127.0.0.1 bind and single-operator posture, and `/app.js` is correctly `no-store` (`src/server.ts:670`). Remediation: add `.generated/` to `.gitignore` (and `git rm --cached` it), or generate the entry outside the repo, or inject the token into the bundle at serve time from memory. Test gap: nothing asserts the token never lands in tracked files.

  5. **MEDIUM — The containment slot lease is decoupled from the timeout the provider actually enforces, so a slot can be reaped while its child is still live (fail-open against the concurrency tooth), or wedge the ceiling for up to 24 hours after a crash.** The wrapper books the lease as `min(spec.timeoutMs ?? 30_000, 86_400_000) + 5s` (`src/capabilities/aggregateContainment.ts:164`), on the theory that "the child was bounded by its own exec timeout" (`:46-47`). The bwrap provider enforces `limit = spec.timeoutMs === undefined ? worldDefault : min(worldDefault, spec.timeoutMs)` with a SIGKILL timer (`node_modules/@godspeedai/cognate-execution/src/bubblewrap.ts:89-91`), and `worldDefault` is operator-configurable up to 300 000 ms (`src/capabilities/containedWorkspace.ts:36`, `bubblewrap.ts:49-51`). Direction A (ceiling violation): with `containmentConfig.timeoutMs = 120000` and a caller that omits `per-exec timeoutMs` (permitted — `cognate-execution/src/capabilities.ts:135` passes it through only when present), the lease expires at ~35 s while the child lives to 120 s; any second admission then reaps the live slot (`aggregateContainment.ts:170-174`) and launches a second child, so more live contained executions run than `maxConcurrent` allows. Direction B (availability): a caller passing `timeoutMs: 86 400 000` gets a provider-side clamp to 300 s but a ~24 h lease; if the holder process dies mid-exec (`--die-with-parent` kills the child, `bubblewrap.ts:80`), the slot stays booked and the ceiling stays shut for up to a day — `reconcileContainmentAtBoot` reaps only already-lapsed slots (`aggregateContainment.ts:219-230`). Remediation: compute the lease from the same bound the provider enforces — clamp `spec.timeoutMs` to the world's validated default/maximum and use `max(worldDefault, clampedSpec) + slack`; assert `worldDefault ≤ 30_000` or pass the world default into the wrapper. Runtime-dependent (kill timing, reap races) but the code paths are static facts. Test gaps: every bwrap journey passes an explicit `timeoutMs` (`test/J-RW-AGGREGATE-CONTAINMENT.test.ts:83,128,173`), so neither direction is exercised; no test runs with a world default above 30 s, and no test passes an inflated `timeoutMs` and crashes the holder.

  6. **LOW — The settings validator and the enforcement parser disagree on the empty object: the documented "clear the quotas" patch is unreachable through the capability.** `parseContainmentQuotas({})` returns `undefined` — explicitly documented as "the explicit 'clear the quotas' patch" (`src/capabilities/aggregateContainment.ts:66-68,86`) — but `isContainmentQuotas` is defined as `parseContainmentQuotas(value) !== undefined` (`src/settings.ts:184-191`), so `{containment: {}}` fails validation and is refused (`src/capabilities/settingsChange.ts:81-84`). The claim that the two "cannot drift apart" (`src/settings.ts:179-181`) is exactly backwards for this value. Impact is fail-closed (quotas can be replaced but never cleared via the UI/capability; `resolveGeneralSettings` treats a stored `{}` as absent, `src/settings.ts:247-249`), but an operator wanting to remove ceilings must hand-edit the store or issue a raw run per finding 2. Remediation: have `isContainmentQuotas` accept the empty object, or remove the documented clear path.

  7. **LOW — Multi-process identity semantics are availability-hostile: one process's boot revokes another live process's browser session, and a cross-process revocation lags up to 2 s.** `supersedeBootSessions` revokes *all* active boot-cause sessions of the operator identity (`src/auth/identity.ts:241-250`), so under the T7-supported two-process posture (`test/J-RW-AGGREGATE-CONTAINMENT.test.ts:139` boots a second app on the same store), process B's boot silently kills process A's freshly issued browser token. The session cache's epoch is process-local, so a revocation committed by process A can be served stale by process B for up to 2 s (`src/auth/identity.ts:196-205` — honestly documented as a read-lag boundary). Both directions fail toward refusal (no security weakening; the revocation tooth holds in the single-process production posture where it is tested). The 2 s lag is untested and the cross-boot revocation is untested.

  8. **LOW — The per-world `prlimit` availability probe is cached forever.** `aggregateContainedRegistry` memoizes one probe per `worldId` with no TTL or retry (`src/capabilities/aggregateContainment.ts:307-317`); a transient failure (bad `cwd`, momentary spawn error) permanently fail-closes every capped execution in that world until restart. Direction is fail-closed (`:280-284` refuses rather than running uncapped), so this is availability only. Conversely, probe-success-then-tool-removal still fails closed at exec time (argv[0] `prlimit` missing → launch error → slot released as `cancelled`, `:292-296`).

  9. **INFORMATIONAL — Ledger hygiene and malformed-row behavior.** Sessions and identities are never pruned, only status-flipped (`src/auth/identity.ts:23-43`), and every authentication is an O(n) scan with `timingSafeEqual` per session (`:185-187`) — fine at single-operator scale, worth a pruning pass later. A structurally-valid-but-corrupt session row (e.g., missing `tokenHash`) makes `candidate.tokenHash.length` throw (`:186`), failing every request closed — a fail-closed brick, not a bypass, but it means one bad row (only writable via finding 1's path or store corruption) is a whole-app auth DoS. `Date.parse(session.expiresAt) <= Date.now()` (`:190`) would pass a NaN `expiresAt` (NaN comparisons are false), but `issueSession`'s validated `ttlMs` (`:139`) makes that unreachable without the same write path.

  10. **INFORMATIONAL — Test-coverage gaps against the teeth, enumerated.** Beyond the gaps named in findings 1-5: (i) no test of the documented 2 s cross-process revocation lag or of two live processes sharing the session ledger; (ii) the CPU-window journeys (`test/J-RW-AGGREGATE-CONTAINMENT.test.ts:73-113`, `test/aggregateContainment.test.ts:121-146`) prove exhaustion fails closed but never prove the window *advances* and work resumes, nor `cpuWindowHours` re-alignment; (iii) no test that a revoked *boot* session's UI stays broken while a second device session keeps working (only the inverse at `test/J-AUTH-SESSION.test.ts:70-71`); (iv) no test that `identity.session.issue` with `ttlHours` extremes (1, 2160) behaves (bounds asserted only in code, `identityAdmin.ts:48`); (v) the strict-input checks cover `superuser` smuggling and case, but not `ttlHours: 0.5` or `cause` length boundaries.

- What the review verified positively:
  - Tokens are 256-bit `randomBytes` under a fixed prefix (`src/auth/identity.ts:69-71`), format-validated before any ledger read (`:73-77`, checked at both `:181` and `:209`), and stored **only** as SHA-256 hashes in the ledger (`:141,151`); `identityOverview` is sanitized — no `tokenHash` leaves the inspect capability (`:256-271`), asserted by `test/J-AUTH-SESSION.test.ts:52-56`.
  - Hash comparison is length-guarded + `timingSafeEqual` (`src/auth/identity.ts:186`); minted tokens cannot collide with the dev format because base64url excludes `:` (which `devTokenAuthenticator` requires, `cognate-protocol-connect-bun/src/index.ts:112-115`).
  - The authenticated caller is derived exclusively from the durable identity — tenant and actor never from any client string (`src/auth/identity.ts:193`); the isolation journey proves a client-claimed tenant is ignored server-side (`test/J-AUTH-TENANT-ISOLATION.test.ts:73-76`) and a forged dev-format token is refused in the production posture (`:78-80`, `test/J-AUTH-SESSION.test.ts:42-43`).
  - Revocation is immediate in-process: every ledger write bumps the process-local epoch and invalidates all cached resolutions (`src/auth/identity.ts:104,115,212`); refusals are never cached (`:215`); cache entries respect both the 2 s TTL and the session's own expiry (`:212,218`). The teeth journey proves a revoked replay is refused with **zero** new durable events, including a mutating `startRun` replay (`test/J-AUTH-SESSION.test.ts:58-68`).
  - Boot sequence is sound: idempotent identity seed, expiry aging, boot-session supersession, then a fresh per-boot issue (`src/server.ts:444-447`); restart invalidates the previous boot token and issues a new one (`test/J-AUTH-SESSION.test.ts:78-84`); expired sessions are aged and refused after restart (`:91-127`).
  - `devAuth` cannot be armed implicitly: only the literal env value `"1"` or the explicit option arms it; anything else — including `"0"` or `"true"` — throws at boot (`src/server.ts:100-106,604`); arming prints a loud warning (`:612-614`); an armed server still refuses raw dev-format strings that don't match and falls through to sessions (`:606-611`); the production entry never logs token material (old `devToken` console log removed, `:703`).
  - Header parsing is anchored, case-sensitive, trims the capture, and refuses empty/garbage/unknown-format tokens (`src/server.ts:609-611`, `test/J-AUTH-SESSION.test.ts:74-76`); whatwg header combining cannot smuggle a second token past the regex.
  - The tightened policy requires BOTH tenant and actor to equal the operator identity for user-kind grants, and system-kind grants remain (`src/server.ts:199-207`); `identityAdmin` independently refuses run contexts and non-operator identities even if the policy were edited (`src/capabilities/identityAdmin.ts:25-30`), with strict unknown-field rejection (`:41-43,64-66`) and bounded `label`/`ttlHours`/`cause` (`:47-49`).
  - The issued token is returned exactly once and is not durably journaled: direct `invoke` returns the value without emitting a durable event (`cognate-runtime-bun/src/invoker.ts:105-115`, `service.ts:187-203`), and run-context invocations — the only path whose results the kernel records on `run.invocation` (`src/projections/sessionTrace.ts:5-8`) — are refused by `operatorOnly`, so the token cannot land in the event log through any legitimate path.
  - Tenant isolation holds by construction for *second* tenants: projections are prefix-partitioned and stripped per caller (`cognate-runtime-bun/src/service.ts:223-232`), thread streams are tenant-namespaced (`service.ts:312,318`), and the journey observes partitions, runs, events, and thread state end to end, including "empty foreign partition indistinguishable from absent" (`test/J-AUTH-TENANT-ISOLATION.test.ts:51-76`).
  - Quota parsing is strict, shared by validator and enforcement (`src/capabilities/aggregateContainment.ts:69-92`, `src/settings.ts:184-191`), fails closed on invalid stored values at admission (`:103-108`), and requires a bookable CPU cap before a window budget is accepted (`:88-90`); aggregate CPU accounting books each execution's FULL kernel cap conservatively (`:135-145`) including reaped slots; the ledger CAS loop reaps and prunes inside the retry (`:165-198`); the containment setting sits at `SETTING_FIELDS` index 11 matching the appended semantic ref (`src/capabilities/settingsChange.ts:39-58`, `src/server.ts:400`).
  - `prlimit` argv construction is injection-safe: only validated positive finite numbers (with integer bounds) flow into fixed `--as=`/`--cpu=` templates, with a `--` separator before the child argv (`src/capabilities/aggregateContainment.ts:257-262`, verified in `test/aggregateContainment.test.ts:135-136`); a configured quota with tooling unavailable refuses and releases the slot (`:280-284`, proven `test/aggregateContainment.test.ts:148-163`).
  - The registry wrap boundary is airtight for current kinds: exact `"linux-bubblewrap"` match (`aggregateContainment.ts:320`), and every registration surface in `src/server.ts` uses the wrapped instance (`:357,389,390,462,478`); the wrap probes through the raw provider so no slot is double-booked by the probe (`:308-317`); non-contained worlds pass through unchanged, as documented.
  - `Bun.serve` hardening that IS present: 127.0.0.1 bind, `maxRequestBodySize` 64 MiB, `no-store` on the token-bearing bundle and the HTML entry, hardened headers on all static/UI/health paths (`src/server.ts:654-675`); `--die-with-parent` and SIGKILL-at-limit in the bwrap provider bound each child (`bubblewrap.ts:80,89-91`).

- Residual boundaries (design-declared; assessed for honest labeling):
  - The 2 s cross-process revocation read-lag and the process-local epoch are explicitly documented at `src/auth/identity.ts:196-205` — honestly labeled, correct freshness class, and the revocation tooth is tested where it is claimed (single process). Not a defect; listed so T9 does not mistake it for silent.
  - The dev authenticator seam is loudly labeled: explicit `"1"` only, boot-fatal on other values, warning when armed, and every test that arms it passes `devAuth: true` explicitly (36 occurrences across the test tree, spot-checked in the helper diffs). The `.sea` journey (`j_auth_session` variants) and `AGENTS.md` both keep the "not production hardened" posture honest.
  - Aggregate containment applies only to `kind === "linux-bubblewrap"` providers; local/ssh/wsl worlds are not aggregate-contained and never were — stated in the code (`aggregateContainment.ts:302-305`) and in the `j_rw_aggregate_containment` variants clause. Aggregate memory is bounded per-execution (RLIMIT_AS) × the concurrency ceiling rather than measured as a live sum — stated at `:13-15` and in the `.sea` variants. Both labels are accurate.
  - Absent quotas keep the historical no-aggregate-quota behavior (`acquireContainedSlot` no-ops, `:162`) — matches the tooth's "configured quota" wording.
  - The single-operator localhost posture (127.0.0.1 bind, no CORS emission) is the outer mitigation for several LOW items; the known security limitation of the single-operator model remains as `AGENTS.md` declares. The modified screenshot binaries were not analyzed (out of scope for a paper review; the identity UI surfaces no token material — `identityOverview` is sanitized).

- Verdict: The change set substantively meets the plan's teeth in the posture where they are claimed: a revoked session's replay is refused with zero durable effect (proven against a real store, including a mutating replay), aggregate quota exhaustion refuses new contained work across processes on one shared store (proven both with stubs and, behind the bwrap gate, with real kernel caps), and cross-tenant access is refused end to end on a shared store — the client-claimed-identity era is genuinely over, token hygiene (randomness, hash-only storage, timing-safe compare, no journaling) is solid, and the dev seam is explicit and loud. However, T8 added two system-owned ledgers without extending the ActionPolicy guard that protects every other system-owned thread, so the *stated* single-operator authorization model has a hole the journeys never test: any provisioned identity inside tenant `local` (or a thief of its token while it is live) can rewrite the session ledger and become the operator, and independently rewrite the operator's containment quotas through the unvalidated `settings.changed` run path. MUST be fixed before this is called settled: (1) extend the `thread.state.update` guard at `src/server.ts:218` to `auth:identity:v1` and `containment:aggregate:v1` (system-only), and add a journey proving a non-operator local-tenant session cannot write either ledger; (2) validate `agent.config` `settings.changed` inputs (or restrict that run's starters) so the containment/spending validators cannot be bypassed by a direct run; (3) stop writing the cleartext boot token into the tracked `.generated/entry.tsx` and untrack/ignore that path; (4) apply the hardening headers to Connect success responses and add the missing successful-response header assertion; (5) fix the containment lease to derive from the provider's enforced bound so a configured world default above 30 s cannot get a live slot reaped. Findings 6-8 should be fixed alongside but do not block the teeth.

## Remediation record (2026-10-17, applied after the review)

Every MUST-fix and the actionable LOW/INFO findings were remediated in the same working tree the
review examined; the full gate (`bun run verify`) and the gated real-bwrap OS journeys were re-run
green afterwards. Dispositions, finding by finding:

1. **HIGH (unguarded ledgers) — FIXED, two layers.** (a) `buildActionPolicy` now refuses
   `thread.state.update` on `auth:identity:v1` and `containment:aggregate:v1` for any non-system
   caller, and additionally refuses raw `thread.state.read` on the identity ledger (token hashes
   are system-only; `identity.inspect` is the sanitized read). (b) `identity.session.issue` now
   refuses to provision a second identity inside the operator's own tenant at all — the exact
   identity the attack needed. New journey assertions prove a provisioned session cannot write
   either ledger, cannot read the identity ledger, and cannot be issued inside the operator tenant
   (`test/J-AUTH-TENANT-ISOLATION.test.ts`).
2. **MEDIUM (unvalidated `settings.changed` runs) — FIXED.** The `agent.config` recording run now
   validates every settings field with the same validators the `settings.change*` capabilities
   use, and rejects unknown fields; an invalid patch never becomes durable (the run fails).
   Journey added: an invalid-containment run ends `failed` and the settings row never appears.
   Combined with 1(b), the operator tenant has exactly one human identity, so no other session
   can write the local-tenant partition at all.
3. **MEDIUM (headers/CSP) — FIXED, and the CSP caught a real violation.** All Connect API responses
   (including successful ones and server streams) now carry the hardening headers; the HTML
   document carries a strict `Content-Security-Policy` (`script-src 'self'`, `frame-ancestors
   'none'`, `base-uri 'none'`, `form-action 'none'`). The header test now asserts a successful
   Connect call and the CSP. The CSP immediately caught a pre-existing inline `onload=` font
   handler; it was replaced with a dynamic stylesheet append from the entry bundle — which also
   preserves the documented "a slow font stylesheet never blocks bootstrap" journey (a
   render-blocking `<link>` broke that test; the dynamic append passes it).
4. **MEDIUM (token in tracked `.generated/entry.tsx`) — FIXED.** `.generated/` is untracked and
   gitignored; the entry is regenerated per boot and never enters version control.
5. **MEDIUM (lease decoupled from the enforced bound) — FIXED.** The wrapper now clamps every
   contained execution to its own 300 s hard bound, PASSES that clamped timeout to the provider
   (the child is killed at the clamped time, so it provably cannot outlive its lease), and books
   the lease as clamp + 5 s. A caller-supplied 24 h timeout leases 305 s, not 24 h. Unit journey
   added asserting the clamp.
6. **LOW (`{}` clear path) — FIXED.** `isContainmentQuotas` accepts the empty object as the
   explicit clear patch (parity with spending); journey added.
